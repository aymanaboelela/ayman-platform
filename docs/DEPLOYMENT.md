# دليل النشر

خطوات تجهيز المنصة على سيرفر حقيقي، بالترتيب.

للخطوات اللي بتتعمل **بعد** النشر وبتحتاج وقت يعدّي (زي تفعيل الـ CSP)،
شوف [`runbooks/launch-runbook.md`](runbooks/launch-runbook.md).

---

## ١. الدومين — أهم قرار، وأصعب واحد ترجع فيه

الموقع والـ API لازم يكونوا **ورا نفس الدومين**:

```
example.com/          →  الموقع (Next.js)
example.com/api/*     →  الـ API (NestJS)
```

**مش** `app.example.com` و `api.example.com`.

ده مش تفضيل — المنصة كلها متبنية عليه. الكوكيز بتستخدم بادئة `__Host-` اللي
بتشترط أصل واحد، ومفيش CORS متظبط في أي مكان لأن المفروض مايكونش محتاج.
لو قسمت الدومين، هتضطر تفتح CORS وترخّي الكوكيز — يعني تفكّك طبقة الحماية
اللي اتبنت من الأول.

لو مضطر تقسم لأي سبب، ده قرار معماري لازم يتراجع، مش تعديل إعدادات.

---

## ٢. متغيرات البيئة

انسخ `.env.example` وغيّر **كل** القيم:

| المتغيّر | ملاحظة |
|---|---|
| `DATABASE_URL` | دور `ayman_runtime` — قراءة وكتابة، **من غير** صلاحية تعديل البنية |
| `DIRECT_DATABASE_URL` | دور `ayman_owner` — للميجريشن بس |
| `BETTER_AUTH_SECRET` | **ولّد واحد جديد**، 32 حرف على الأقل |
| `BETTER_AUTH_URL` · `APP_URL` | نفس الدومين، بـ `https://` |
| `REDIS_URL` | مطلوب للـ API (حدود الطلبات)، واختياري للويب (الكاش) — شوف خطوة ٥ |

السيرفر بيرفض يشتغل أصلًا لو أي متغيّر ناقص أو شكله غلط، وبيقولك كل الغلطات
مرة واحدة. ده مقصود — أحسن من إنه يشتغل وينهار بعدين.

## ٣. الداتابيز

```bash
psql -d postgres -f scripts/db-bootstrap.sql     # بعد ما تغيّر الباسوردات اللي جواه
pnpm --filter @ayman/api exec prisma migrate deploy
pnpm --filter @ayman/api exec prisma generate
pnpm db:seed
```

**⚠️ الباسوردات اللي في `scripts/db-bootstrap.sql` للتطوير المحلي بس** — مكتوبة صريحة
في الملف عن قصد. غيّرها من مدير أسرار قبل أي سيرفر حقيقي.

**اتأكد إن الدور المحدود شغال صح:**

```bash
psql "postgresql://ayman_runtime:PASSWORD@HOST/DB" -c "CREATE TABLE app.x (id int);"
# لازم يرد: ERROR: permission denied for schema app
```

لو الأمر ده **نجح**، وقف. ده الضابط اللي بيمنع أي ثغرة SQL من إنها تعدّل بنية
الداتابيز أو تعمل دالة خبيثة.

## ٤. جوجل وآبل

**جوجل:** OAuth client من Google Cloud Console، والـ redirect URI يبقى
`https://YOURDOMAIN/api/auth/callback/google`.

**آبل — دي مختلفة، اقرا كويس:**

الـ `client_secret` بتاع آبل **مش مفتاح ثابت**. ده JWT بتولّده إنت من ملف `.p8`،
و**بينتهي كل 6 شهور كحد أقصى**.

يعني: بعد 6 شهور من النشر، تسجيل الدخول بآبل هيقف فجأة، من غير ما يتغيّر أي كود،
ومن غير رسالة خطأ واضحة.

**حط تذكير يتجدّد كل 5 شهور من دلوقتي.** محتاج: Team ID، Key ID، وملف `.p8`.

وكمان: **آبل مستحيل تتجرّب محليًا** — بترفض `http://localhost` من أساسها.
أول تجربة حقيقية ليها هتكون على الدومين.

## ٥. Redis — مستخدمين اتنين، وبيفشلوا بالعكس عن قصد

نسخة Redis واحدة بتخدم حاجتين مختلفتين تمامًا:

**١. حدود الطلبات (الـ API).** لو شغّلت نسختين من الـ API من غير `REDIS_URL`
مظبوط، كل نسخة هيبقى عندها عدّاد لوحدها — والحد الفعلي بيتضاعف بعدد النسخ من
غير ما حد ياخد باله. يعني حد "10 محاولات دخول" بنسختين بيبقى فعليًا 20.

**٢. كاش `'use cache'` (الويب).** `apps/web/cache-handler/redis.js`. من غيره
كل نشرة بتصفّي الكاش — و`getBranding()` بتتقرا في الـ root layout يعني على
مسار كل صفحة، فأول زائر بعد كل نشرة بيدفع تمن قراءة باردة. وكمان `updateTag()`
بتوصل لنسخة واحدة بس، فالأدمن بيحفظ ونسخة تانية تفضل تقدّم القديم.

### الفرق في التعامل مع العطل — ده مقصود ومتعمّد

| | Redis واقع |
|---|---|
| **حدود الطلبات** | بتفشل **مقفولة** — خطأ 500 |
| **الكاش** | بيفشل **مفتوح** — بيرجع يشتغل بالذاكرة |

حد طلبات مش شاطف Redis يبقى **مفيش حد أصلاً**، فالخطأ هو الرد الآمن. كاش مش
شاطف Redis يبقى مجرد كاش أبطأ. لو الاتنين اتعاملوا بنفس الطريقة، Redis كان
هيبقى نقطة فشل واحدة للمنصة كلها.

### سقف الذاكرة والديمومة

البوكس المرجعي **٢ جيجا رام** (شوف `runbooks/vps-setup.md`)، وعليه أربع خدمات:
postgres وapi وweb وredis. الإعدادات دي مبنية على الرقم ده.

**السقف.** Redis افتراضيًا `noeviction`: لما الذاكرة تمتلي، الكتابة بترجع
أخطاء. ده كان مقبول وهو شايل عدّادات صغيرة بس؛ بقى مش مقبول بعد ما الكاش دخل —
الكاش ملوش سقف طبيعي، ولما يملا Redis، كتابة العدّادات بتفشل هي كمان، وهي بتفشل
**مقفولة**: 500 على المنصة كلها.

السقف دلوقتي `--maxmemory ${REDIS_MAXMEMORY:-128mb}`. زوّده من `REDIS_MAXMEMORY`
في ملف `.env` بتاع compose لو سيرفرك أكبر — مثلاً `REDIS_MAXMEMORY=512mb` على
بوكس ٤ جيجا. الافتراضي محافظ عن قصد: لو صغير على استخدامك، النتيجة إن الكاش
بيتشال أكتر — أبطأ، مش مكسور.

**السياسة `volatile-lru`.** بتشيل المفاتيح اللي ليها TTL بس، وده كل المفاتيح
هنا: الكاش بيحط `EX` والـ throttler بيحط `PEXPIRE`. وLRU بيحمي العدّادات من غير
ما نقول له — بتتلمس في كل طلب فهي الأحدث استخدامًا دايمًا، والكاش الأبرد بيتشال
الأول. (`volatile-ttl` كان هيعمل العكس: يشيل أقصر TTL، يعني العدّادات.) وأسوأ
حالة إن عدّاد يتشال فتبدأ نافذته من الأول — تجاوز بسيط لمرة واحدة، مقابل
`noeviction` اللي بيرمي المنصة كلها على 500.

**مفيش ديمومة، وده مقصود.** الإعداد بقى `--save ""` و`--appendonly no`.

الصورة الرسمية بتيجي بنقاط حفظ مدمجة (`3600 1 300 100 60 10000`)، فلازم
`--save ""` صراحةً عشان تتلغي. وكان الإعداد هنا `--save 60 1` — وده كان معقول
وإحنا شايلين عدّادات بس، لأن شرط "مفتاح واحد اتغيّر" كان بيتحقق نادرًا. الكاش
بيكتب باستمرار، يعني الشرط بقى متحقق **دايمًا**، يعني fork كل دقيقة. والـ fork
بينسخ الذاكرة عند الكتابة، على بوكس ٢ جيجا شغّال عليه postgres وapi وweb.

ومحدش هنا محتاج الديمومة: عدّادات الحدود TTL بتاعها قصير، والكاش كاش. أسوأ
نتيجة لإعادة تشغيل Redis إن نوافذ الحدود تبدأ من الأول والكاش يبرد — وده بالظبط
اللي كان بيحصل كل نشرة قبل ما الكاش يدخل أصلاً.

المتسابة `redisdata` سايبينها موصولة على `/data` رغم إن مفيش كتابة عليها، عشان
رجوع الديمومة يبقى تغيير سطر واحد بدل تغيير في التخزين.
