# Agent discovery

How this site presents itself to AI agents and assistants, what is served from code, and
the one piece that is **not** code and has to be published in Cloudflare DNS by hand.

Prompted by an [isitagentready.com](https://isitagentready.com) scan of
`aymanaboelela.com` on 2026-08-05.

## What the app serves (already live, no action needed)

Everything below is generated by route handlers in `apps/web/app`. The paths are declared
once in [`apps/web/lib/agents/discovery.ts`](../../apps/web/lib/agents/discovery.ts) —
add a document there, not as a literal in five files.

| URL | Media type | What it is |
| --- | --- | --- |
| `/.well-known/api-catalog` | `application/linkset+json` | RFC 9727 API catalog |
| `/openapi.json` | `application/vnd.oai.openapi+json;version=3.1` | `service-desc`, generated from the Zod contracts |
| `/docs/api` | `text/markdown` | `service-doc`, the prose version |
| `/auth.md` | `text/markdown` | Auth.md — states there is nothing to obtain |
| `/llms.txt` | `text/plain` | llmstxt.org index, live course list |
| `/.well-known/agent-skills/index.json` | `application/json` | Agent Skills Discovery v0.2.0 |
| `/.well-known/agent-skills/{name}/SKILL.md` | `text/markdown` | Each skill, hashed in the index |
| `/robots.txt` | `text/plain` | Content signals + crawl rules |
| `/{page}.md`, or `Accept: text/markdown` | `text/markdown` | Markdown twin of every public page |

Plus, on every public HTML response: an RFC 8288 `Link` header pointing at all of the
above, and `Vary: Accept` on any route with a markdown twin.

WebMCP tools (`search_courses`, `get_course`, `get_study_path`) are registered from
`(site)/layout.tsx` where the browser supports `navigator.modelContext`.

### Content signals

`robots.txt` carries `Content-Signal: search=yes, ai-input=yes, ai-train=no`.

Decided by Ayman on 2026-08-05: index it, let assistants read and cite it, do **not** let
it become training data. Changing any of the three is his call, not a maintenance
decision — the rationale is in
[`apps/web/app/robots.txt/route.ts`](../../apps/web/app/robots.txt/route.ts).

## DNS-AID — MANUAL, not yet published

`_index._agents.aymanaboelela.com` does not exist. This is the one scan finding that no
code change can fix: it is a DNS record, and this repo does not manage DNS.

⚠️ **Read the caveat before publishing.** DNS-AID is an
[individual Internet-Draft](https://datatracker.ietf.org/doc/draft-mozleywilliams-dnsop-dnsaid/),
not an RFC and not adopted by the dnsop working group. The SvcParamKeys below (`well-known`,
`cap`, `realm`) are **not registered with IANA** and may be renamed or dropped before the
draft stabilises — or the draft may expire and go nowhere. Publishing costs one DNS record
and breaks nothing if the spec moves; just do not treat these names as stable.

### The record to add

One record, not three. `_a2a._agents` and `_mcp._agents` are deliberately **not** published:
this platform runs neither an A2A agent nor an MCP server, and advertising an endpoint that
does not answer is the DNS version of the fake OAuth metadata `/auth.md` declines to serve.

```zone
_index._agents.aymanaboelela.com. 3600 IN SVCB 1 aymanaboelela.com. (
    alpn="h2,h3"
    port=443
    well-known="api-catalog"
)
```

`SVCB 1 <target>` is ServiceMode (priority ≥ 1), which is what the draft requires —
priority `0` would be AliasMode and carry no parameters. `well-known="api-catalog"`
resolves against RFC 8615, i.e. it points an agent at
`https://aymanaboelela.com/.well-known/api-catalog`, which is the real entry point to
everything in the table above.

### Publishing it in Cloudflare

1. Cloudflare dashboard → `aymanaboelela.com` → **DNS** → **Records** → **Add record**.
2. Type **SVCB**. Name `_index._agents`. TTL `Auto` is fine.
3. Priority `1`, Target `aymanaboelela.com`.
4. Value: `alpn="h2,h3" port=443 well-known="api-catalog"`.
5. Proxy status is **DNS only** — an underscore-prefixed SVCB record is not proxiable, and
   the orange cloud is not offered for it.

#### ⚠️ «Value for SVCB record is invalid» means the PRIORITY is wrong

Observed 2026-08-05 while adding this record. Cloudflare rejects the form with an error
pointing at the **Value** field when the actual cause is **Priority `0`**.

Priority `0` is AliasMode, and AliasMode records carry **no SvcParams at all**. So the
moment `alpn=…` is typed alongside a `0`, the record is self-contradictory — and
Cloudflare blames the params rather than the number that made them illegal. Setting
Priority to `1` (ServiceMode) clears it with no change to the Value.

Do not go debugging the param string. Check the priority first.

If the dashboard rejects the `well-known` key (Cloudflare validates SvcParams against the
registered set, and this one is not registered), publish the record with `alpn` and `port`
alone. It still resolves as a valid DNS-AID entry point; the `well-known` hint is
additive, and `/.well-known/api-catalog` is discoverable from the `Link` header regardless.

### DNSSEC

The scan also asks for the discovery zone to be signed. Cloudflare → **DNS** → **Settings**
→ **DNSSEC** → *Enable*.

✅ **`aymanaboelela.com` is registered with Cloudflare Registrar**, so that is the whole
procedure. Cloudflare is both the registrar and the DNS provider, so it publishes the DS
record at the parent zone itself — the dashboard shows *"DNSSEC is pending while we
automatically add the DS record on your domain"* and then completes on its own. Confirmed
2026-08-05.

⚠️ The above is true **only** because of where the domain is registered. If it is ever
transferred to an outside registrar, enabling DNSSEC here stops being sufficient: the DS
record has to be copied to that registrar by hand, and skipping it leaves the zone
unsigned while the Cloudflare dashboard still reads as success. That is the usual way a
zone ends up "DNSSEC enabled" and unvalidated.

### Verifying

```bash
dig +short _index._agents.aymanaboelela.com SVCB
dig +dnssec _index._agents.aymanaboelela.com SVCB | grep -q 'flags:.* ad' && echo "signed"
```

## Deliberately not implemented

Three scan findings were declined on the merits. Each is a decision, not a backlog item —
if a future scan flags them again, this section is the answer.

### OAuth/OIDC discovery metadata

`/.well-known/openid-configuration` and `/.well-known/oauth-authorization-server` are
**not** published, because this platform is an OAuth *client* (Google and Apple sign-in via
better-auth), not an authorization *server*. There is no token endpoint, no `jwks_uri` and
no client registration to describe.

Publishing them anyway would turn the scan green by making a false, machine-readable claim
that agents can obtain tokens here — on a site whose accounts belong to secondary-school
students. `/auth.md` states the true position instead, and satisfies the Auth.md finding.

If a real agent-facing OAuth server is ever built (better-auth ships an OIDC provider
plugin), publish these then, and only then.

### OAuth Protected Resource Metadata

`/.well-known/oauth-protected-resource` requires an `authorization_servers` array. There is
no authorization server to name. Same reasoning as above.

### Web Bot Auth

`/.well-known/http-message-signatures-directory` publishes a JWKS so **other** sites can
verify requests *this* site sends as a bot. This site crawls nothing and sends no
outbound bot traffic, so the directory would advertise a signing key that never signs
anything — a key to rotate and protect for no benefit. The scan itself marks this one
informational.

Revisit if the platform ever grows an outbound crawler or fetcher.
