# Plan 3 — Content & Catalog: end-to-end verification

Recorded by hand, driving a real browser (chrome-devtools MCP) plus `psql` and `curl`,
against `pnpm dev`-equivalent processes: `apps/api` on port 3301 (a fresh `nest start
--watch` — the pre-existing process on 3300 was serving a stale build with no content
routes, so a second instance was started per the task's own instructions rather than
killing a process that wasn't mine) and `apps/web` on port 3200 with `API_ORIGIN`
pointed at 3301.

Every line below is an observation, not an expectation — where something did not work
as specified, that is called out explicitly rather than glossed over.

## 1. Author, publish, appear

1. **Create a course.** Registered `admin-plan3@example.com`, promoted to `role='admin'`
   via `psql` (no admin-signup flow exists yet), completed onboarding via a direct
   `student_profiles` insert (`onboarding_completed_at = now()`) to satisfy `proxy.ts`'s
   redirect matrix without walking the student-facing onboarding wizard. Created
   **أساسيات الخوارزميات** (`algorithms-basics`), البكالوريا / الصف الثاني / مسار
   الهندسة وعلوم الحاسب / البرمجة وعلوم الحاسب.
   → Landed on `/admin/courses/<id>`, status **مسودة** (draft). Observed.

2. **Visit `/courses`.** → The new course is absent (`curl` grep for its title:
   0 matches). Observed.

3. **Added a section** ("الفصل الأول: مقدمة") and **four lessons**: `فيديو: ما هي
   الخوارزمية؟` (video), `قراءة: تعريف الخوارزمية` (text), `مرفق: ورقة تدريبات`
   (attachment), `اختبار: مراجعة الفصل الأول` (quiz).
   → `psql`: all four rows present with the correct `kind` and increasing `position`
   (0–3). Observed.

4. **Pasted `https://www.youtube.com/watch?v=dQw4w9WgXcQ&list=PLxxxx&si=track`** into
   the video lesson's URL field, duration 240s.
   → UI immediately showed `dQw4w9WgXcQ` next to the lesson (11 characters). `psql`:

   ```
   SELECT external_id, duration_seconds FROM app.lesson_videos ORDER BY created_at DESC LIMIT 1;
    external_id | duration_seconds
   -------------+------------------
    dQw4w9WgXcQ |              240
   ```

   No `list`, no `si`, no host — exactly 11 characters. Observed.

5. **Pasted `<p>مرحبا</p><script>alert(1)</script><iframe src="https://evil.example">
   </iframe><a href="https://example.com">لينك</a>`** into the text lesson.
   → `psql`:

   ```
   SELECT body_html FROM app.lesson_texts ORDER BY created_at DESC LIMIT 1;
    <p>مرحبا</p><a href="https://example.com" rel="noopener noreferrer nofollow" target="_blank">لينك</a>
   ```

   No `<script`, no `<iframe`, anchor carries the forced `rel`. Observed.

6. **Drag-reorder.** Pointer-simulated drag via the chrome-devtools `drag` tool did
   **not** register a dnd-kit drag session (`active.id === over.id` in the resulting
   announcement; no request fired) — a tooling limitation, not a product bug: dnd-kit's
   `PointerSensor` needs a real sequence of `pointermove` events crossing the 8px
   activation distance, which a single synthetic "drag from A to B" command does not
   reliably produce. **Keyboard reordering** (dnd-kit's documented equivalent, and one
   of this task's own explicit checks) worked correctly: focused the last lesson's
   drag handle, pressed **Space → ArrowUp → ArrowUp → ArrowUp → Space**. The quiz
   lesson moved to position 1 and the live region announced
   `"اتسابت في الترتيب رقم 1"`. A second keyboard move (Space → ArrowDown → Space)
   moved it to position 2. Each of the two completed drags produced **exactly one**
   `PATCH /api/admin/sections/:id/lessons/order` in the API's pino log (200, 31–38ms),
   never one per intermediate arrow-key step, carrying the full 4-id ordered array.
   `psql` confirmed the final order matches what the UI showed. The **debounce
   collapsing many rapid drags into one write** is proven deterministically by
   `use-debounced-reorder.test.ts` (fake timers, 5 tests) — a live MCP session cannot
   reliably fire two drags within the 600ms window through round-trip tool calls, so
   that specific timing claim rests on the unit test, not this manual run.

7. **Published the course while every lesson was still unpublished.** → Blocked.
   The UI showed exactly `لازم يكون فيه محاضرة منشورة واحدة على الأقل`, status stayed
   **مسودة**. Observed.

8. **Published the section, published the video lesson, then published the course.**
   → All three succeeded; course status became **منشور**. Observed.

9. **Reloaded `/courses`.** → The course appeared immediately (no rebuild, no
   restart) — `updateTag(TAG_COURSES)` inside `setCourseStatusAction` invalidating the
   list's coarse tag. Observed.

10. **Opened `/courses/algorithms-basics` anonymously** (`curl`, no cookies).
    → Renders. `curl` (no JS) shows the lesson title `فيديو: ما هي الخوارزمية؟` and
    the course description in the raw response body — confirmed SSR'd, not
    client-injected. Observed.

11. **`curl -s http://localhost:3200/sitemap.xml | grep algorithms-basics`** →
    present, with `<lastmod>` from `updatedAt`. Observed.

12. **Unpublished the course, reloaded `/courses`.** → Gone immediately. `psql`
    confirms `status='draft'`.
    → **Concern, not silently passed over:** `curl -s -o /dev/null -w '%{http_code}'
    http://localhost:3200/courses/algorithms-basics` returned **200, not 404** — see
    "Known limitation" below. The API itself (`GET /api/catalog/courses/algorithms-
    basics`) correctly returns a genuine **404**, and the page's rendered body is the
    not-found UI with zero course data in it (verified via `curl` body inspection for
    both this slug and a slug that was never created at all — identical body, identical
    wrong status). The data-level boundary holds; the HTTP status line on the Next.js
    page does not.

13. **As the logged-in student** (`student-plan3@example.com`, registered separately),
    `POST /api/courses/019f9def-bd50-752b-baf1-9689d8bb6730/enroll` (the **published**
    `python-basics` course — `algorithms-basics` was draft again by this point and
    correctly 404s on enroll too) via the browser's own `fetch`, carrying the
    session cookie and `x-csrf-token` automatically.
    → **201**, body `{"enrollmentId":"...","access":{"allowed":true,"grantId":"...",
    "scope":"platform","validUntil":null}}`. `psql`:

    ```
    SELECT scope, source, valid_until FROM app.access_grants ORDER BY created_at DESC LIMIT 1;
      scope   |  source   | valid_until
    ----------+-----------+-------------
     platform | auto_free |
    ```

    Free is a **row**, never a boolean. Observed.

14. **As that same student:** `PATCH /api/admin/courses/019f9def-...` → **403**.
    `PATCH /api/admin/courses/019f9def-.../status` → **403**. `GET
    /api/catalog/courses` → **200** (public). The course's title in the DB was
    confirmed unchanged after the attempted PATCH. Observed.

## 2. Design constraints, read from computed style

On `/courses` (light mode, default): a `Card`'s computed `box-shadow` was
`rgba(0,0,0,0.07) 0px 2px 5px 0px, …` (the `--shadow-sm` token) — a real, visible
shadow. Switching to dark mode (`document.documentElement.setAttribute('data-theme',
'dark')`, matching the app's own FOUC-prevention script) on the **same element**:
computed `box-shadow` became **five fully-transparent layers**
(`rgba(0,0,0,0) 0px 0px 0px 0px, …`) — no shadow, as designed. `border-radius` read
`8px` in both themes (`--r-lg`, the plan's stated ceiling). The amber "مجاني" badge
rendered flat (a solid `border`/`background` from `color-mix`, no gradient stop) in
both themes. RTL layout (breadcrumbs, badges, card content) was correct in both.

## 3. JSON-LD

The published course page carried **3** `<script type="application/ld+json">` blocks
(Organization, Course, BreadcrumbList) — no `VideoObject`, correctly, because this
course's video lesson is not marked as a free preview. Pasted into
`https://validator.schema.org` (Code Snippet mode; ASCII placeholder strings were
substituted for the Arabic field values only because the validator's embedded editor
would not accept simulated paste/keystroke events for non-Latin text through browser
automation — every key, nesting level and `@type` is byte-for-byte what the app
actually emits): **Organization, Course, BreadcrumbList — each 0 errors, 0 warnings.**
Constructed the `ItemList` (3-course minimum) and `VideoObject` shapes directly from
`courseListJsonLd`/`videoObjectJsonLd` and validated those too: **0 errors, 0
warnings** for both. `robots.txt` disallows `/admin`, `/dashboard`, `/onboarding`,
`/settings`, `/api/`, `/dev/` and points at the sitemap; the sitemap lists `/`,
`/courses`, and one `<url>` per published course with no draft present.

## 4. Caching

Three reloads of `/courses` produced **one** new `GET /api/catalog/courses` in the
API's pino log (measured delta across three `curl`s: `before=3 after=4`). Editing the
published course's title updated `/courses/<slug>` immediately (read-your-own-write
via `updateTag(courseTag(id))`) while `/courses` kept showing the old title until the
course was next published/unpublished (only that action touches `TAG_COURSES`) —
the per-entity vs. coarse split working exactly as designed, observed rather than
assumed.

## Known limitation: `notFound()` status code under Cache Components

**Concern for the reviewer.** A draft/removed course's public page renders the
not-found UI with **zero** course data — the content-level boundary is intact — but
the outer HTTP status code is **200**, not 404, both in `next dev` and in a
`next build && next start` production run. This was investigated in depth (see
`apps/web/app/(site)/courses/[slug]/page.tsx`'s comment on `generateStaticParams` for
the full account): the response streams under this app's global `cacheComponents:
true`, the initial 200 status line commits before the per-request `notFound()` call
resolves (this route has no `generateStaticParams` coverage for an unknown/draft
slug), and every officially documented mitigation was tried — moving the check
before any other `await`, removing `loading.tsx`, removing `'use cache'` from
`getCourse`, adding `generateStaticParams`, and testing bot user-agents against
`htmlLimitedBots` — with no change to the outer status code. `dynamicParams = false`
does force a real 404, but was rejected: it would 404 any course published after the
last build until the next deploy, defeating the entire point of `updateTag()` making a
publish visible immediately (Definition of Done item, verified above in §1.9). The
actual data boundary is fully enforced at the API (`GET
/api/catalog/courses/:slug` returns a genuine 404 for both a nonexistent and a draft
slug, verified directly with `curl`), and the sitemap never lists a non-published
course. This is flagged as a real, unresolved gap against the literal
`curl -w '%{http_code}'` → 404 check, not claimed as fixed.
